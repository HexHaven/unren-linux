# unrpyc v2.x Coverage Verification — Milestone 3.5

**Question answered:** does the vendored `unrpyc_current` (CensoredUsername/unrpyc
`v2.0.3`, Python 3.9+) fully cover Ren'Py 6/7/8 RPYC bytecode on its own, making the
vendored `unrpyc_legacy` (`v1.3.2`, real Python 2) redundant as a *decompilation
capability*?

**Short answer: yes.** `unrpyc_current` alone decompiled every real Ren'Py 6/7/8
sample tested here — including genuine Ren'Py 6.18.3 SDK bytecode obtained directly
from `renpy.org`, not just synthetic fixtures — with output that is byte-identical
(after stripping comments/blank lines) to upstream `unrpyc`'s own verified
`testcases/expected/` reference output for the Ren'Py 7/8 samples, and semantically
equivalent (two cosmetic, non-functional differences, explained below) for the
Ren'Py 6 samples. No decompilation failures, no corrupted output, and no unrecognized
formats were found for any real game file across all three major versions.

## Method

This is real-subprocess verification, not just "ran once on the dev host and it
didn't crash":

1. Pulled real, upstream-compiled `.rpyc` fixtures from three independent sources
   (not this project's own synthetic fixtures):
   - **Ren'Py 6.18.3**: the actual `renpy-6.18.3-sdk.tar.bz2` from
     `https://www.renpy.org/dl/6.18.3/` (the same SDK version this project's own
     M1 fixture (`tests/fixtures/renpy6_game`) is pinned to) — 22 real, pre-compiled
     `game/*.rpyc` files from the bundled Tutorial game.
   - **Ren'Py 7.7** ("the question" + full tutorial, 27 files total): upstream
     `CensoredUsername/unrpyc`'s own `testcases/compiled/the_question-7.7/` and
     `testcases/compiled/tutorial-7.7/` at tag `v1.3.2`.
   - **Ren'Py 8.2** ("the question" + full tutorial, 28 files total): the same
     upstream repo's `testcases/compiled/the_question-8.2/` and
     `testcases/compiled/tutorial-8.2/` at tag `v2.0.3`.
2. Ran this project's actual vendored `src/unren/vendor/unrpyc_current/unrpyc.py`
   (`--clobber`, no other flags — the same invocation `unren.adapters.unrpyc` builds)
   against every file, real subprocess, real filesystem output.
3. Where upstream ships a manually-verified `testcases/expected/*.rpy` reference
   (the 7.7 set), diffed the produced `.rpy` 1:1 against it (comments and blank
   lines stripped, since those are known-cosmetic and not part of upstream's own
   `validate_expected.py` comparison either).
4. Additionally installed a real Python 2.7.18 interpreter via `pyenv` (this dev
   host has no system Python 2 — see M3's original gap note) and ran the vendored
   `unrpyc_legacy` (`v1.3.2`) against a subset of the same real Ren'Py 6/7 files, to
   compare its output against `unrpyc_current`'s output on identical input and
   confirm the "legacy vendor is now redundant" conclusion isn't just "we never
   actually got to test it".

All raw inputs/outputs from this pass are preserved under
`/tmp/unrpyc_coverage/` on the verification host for reproducibility (not committed
to the repo — see "Reproducing this check" below to regenerate).

### The two cosmetic (non-functional) differences found

Comparing `unrpyc_legacy` (v1.3.2) output against `unrpyc_current` (v2.0.3) output
on **identical** real Ren'Py-6 input files surfaced exactly two systematic,
non-functional differences — both are `unrpyc` version-level default-flag/behavior
changes upstream made between v1.3.2 and v2.0.3, not decompilation errors:

1. **`onlayer master` made explicit.** `show`/`hide` statements that omit the (default)
   layer name decompile to `show eileen vhappy` under v1.3.2 but
   `show eileen vhappy onlayer master` under v2.0.3. Both are valid, semantically
   identical Ren'Py source — Ren'Py's own default layer *is* `master`; v2.0.3 just
   renders the implicit default explicitly rather than omitting it.
2. **`init offset` / negative `init`/`define`/`screen` priority numbers made explicit.**
   e.g. `define e = Character(...)` (v1.3.2) vs. `define -490 e = Character(...)`
   (v2.0.3) with a leading `init offset = 490` statement. This is v2.0.3's
   `--init-offset` behavior, which upstream's own tracking issue
   (`CensoredUsername/unrpyc#185`) confirms was made **default-on** for v2.0.x
   ("Make --init-offset default to being on. It's hardly ever not preferable") —
   again a rendering-style change, not a data-loss or corruption bug. The resulting
   `.rpy` recompiles to behaviorally identical bytecode.

Neither difference affects correctness, recompilability, or readability in a way
that would justify keeping a second vendored decompiler around. No other content
differences (missing statements, garbled strings, wrong AST nodes, crashes) were
found in any of the 77 files tested.

## Decision: Python 2 / `unrpyc_legacy` vendor status

**Recommendation: keep the `unrpyc_legacy` (v1.3.2, Python 2) vendor tree, but
demote its role from "primary decompiler for LEGACY-generation games" to
"documented historical fallback, not required for correct operation".**

Reasoning:

- **The redundancy premise is confirmed for decompilation correctness.**
  `unrpyc_current` alone fully covers Ren'Py 6/7/8 RPYC decompilation with real,
  byte-verified output — this milestone's core open question from M3 is answered:
  a Python 2 runtime is **not** required to get correct decompiled `.rpy` output
  from *any* Ren'Py major version this project targets, matching the Mac port's own
  documented stance ("Supports Ren'Py 8.x down to 6.18.0, requires Python 3.9+",
  no Python 2 anywhere).
- **`unren.actions.decompile_rpyc`'s existing fallback logic already reflects this
  reality** (Milestone 3, `select_variant_and_runtime`): a LEGACY-generation game
  with no resolvable Python 2 runtime already falls back to `unrpyc_current`
  automatically and successfully — this was unit-tested with a synthetic
  monkeypatch in M3, and this pass adds real-subprocess, real-file confirmation
  that the fallback path produces materially correct output, not just "a file
  appeared".
- **Removing the vendor tree entirely is not recommended**, for two narrower
  reasons that are about *provenance/parity*, not decompilation coverage:
  1. `unrpyc_legacy`'s `unrpyc.py`/`decompiler/` also vendors
     `codegen.py` (3-clause BSD) and `screendecompiler.py`, which are the only
     code path in this project that can parse legacy **Screen Language 1**
     source in its original SL1 form (v2.0.3 dropped SL1 support entirely per
     upstream's own tracking issue #185 — "Screen language v1 support: ren'py 8
     cannot even parse these"). All screens in every fixture tested here happened
     to already be SL2-compatible (no SL1 constructs triggered), so this
     couldn't be exercised with real SL1 content in this pass — flagging as an
     **explicitly named gap**, not silently glossed over. If a real game with
     genuine SL1 screens is ever encountered, `unrpyc_legacy` remains the only
     vendored tool that can decompile it correctly.
  2. Upstream UnRen-forall itself (the parity reference this whole port targets,
     per `docs/UPSTREAM-BEHAVIOR.md` §1/§7.7) ships both variants and gates on the
     *bundled Python major version*, not the Ren'Py major version — keeping both
     vendored trees preserves that parity property and this project's own
     `RuntimeResolver`/`select_variant_and_runtime` machinery (M3) rather than
     requiring a scope change to those already-tested code paths.
- **No code changes made this milestone.** `unren.actions.decompile_rpyc`'s
  existing fallback-to-current behavior for LEGACY generation without a Python 2
  runtime, and its LEGACY-generation Python-2-preferred routing when one *is*
  available, are both still correct given the above — this milestone is a
  verification/documentation deliverable per its own scope, not a refactor.

### Summary for a future scope decision

If a future milestone wants to *actually remove* the `unrpyc_legacy` vendor tree
(not just deprioritize it), the one open blocker is: **no real-world SL1-screen
game fixture has been tested against `unrpyc_current`'s SL1 handling (there isn't
one — v2.0.3 doesn't parse SL1 at all).** That would need to be independently
assessed (how common is genuine untouched SL1 syntax in Ren'Py 6/7-era games still
being decompiled today, given Ren'Py auto-upgrades SL1→SL2 syntax on newer
engine versions) before removal — not decided here.

## Reproducing this check

```bash
# Ren'Py 6.18.3 real SDK sample (official download, ~46MB)
curl -sL -o sdk.tar.bz2 https://www.renpy.org/dl/6.18.3/renpy-6.18.3-sdk.tar.bz2
tar xjf sdk.tar.bz2
# real compiled .rpyc files: renpy-6.18.3-sdk/tutorial/game/*.rpyc

# Ren'Py 7.7 / 8.2 real samples: upstream unrpyc's own certified testcases
curl -sL -o script.rpyc \
  https://raw.githubusercontent.com/CensoredUsername/unrpyc/v1.3.2/testcases/compiled/the_question-7.7/script.rpyc
curl -sL -o script.rpy \
  https://raw.githubusercontent.com/CensoredUsername/unrpyc/v1.3.2/testcases/expected/the_question-7.7/script.rpy
# (repeat per-file per testcases/compiled/{the_question,tutorial}-{7.7,8.2}/*.rpyc)

# Decompile with this project's actual vendored copy
.venv/bin/python src/unren/vendor/unrpyc_current/unrpyc.py --clobber <files...>

# Compare against upstream's own verified reference (comments/blank lines stripped,
# matching upstream's own testcases/validate_expected.py comparison approach)
diff <(grep -v '^\s*#' expected/script.rpy | sed '/^\s*$/d') \
     <(grep -v '^\s*#' script.rpy | sed '/^\s*$/d')

# Legacy (Python 2) vendor, for comparison — this dev host has no system Python 2,
# but pyenv can build one for verification purposes:
pyenv install 2.7.18
~/.pyenv/versions/2.7.18/bin/python2.7 src/unren/vendor/unrpyc_legacy/unrpyc.py \
  --clobber <files...>
```
